# CabinGuard 产品与技术决策记录

这份记录用于回答面试中的“为什么这样做”，而不只是展示“做了什么”。

## D01：先验证可信任务闭环，不接真实车控

- 问题：真实 CAN、地图和充电接口会显著扩大权限、合规和硬件成本，容易掩盖核心产品假设。
- 决策：用可控模拟状态验证上下文读取、风险说明、确认、执行和结果核验。
- 放弃：直接包装成真实车控平台。
- 代价：不能证明硬件集成或量产可靠性；作品集中必须明确边界。
- 下一验证：接 VSS/WebSocket 车辆模拟器，制造状态延迟和动作失败。

## D02：模型负责规划，应用负责授权和执行

- 问题：Prompt 可以引导模型，但不能作为安全边界。
- 决策：模型只输出工具调用；Python 主后端用 Pydantic，Next.js 兼容后端用 Zod，并统一通过状态读取前置、风险规则和导航授权决定是否执行。
- 放弃：让模型直接修改状态，或只靠“不要误操作”的系统提示词。
- 代价：规则和工具契约需要持续维护，但行为更可解释、可测试。
- 成功信号：恶意或错误参数不会改变状态；没有工具结果时不能宣称完成。

## D03：保留稳定演示与开放 Agent 两条链路

- 问题：完全依赖外部模型会让面试演示受网络和模型波动影响；完全确定性流程又无法展示 Agent 规划。
- 决策：首页使用 LLM 增强理解与本地回退，Agent Lab 展示真实多轮 Tool Calling。
- 放弃：用一次随机成功的对话代表产品可靠性。
- 代价：产生重复实现和策略漂移风险。
- 收敛方案：已统一确认与导航策略；下一步让主页和 Realtime 调用同一个服务端执行器。

## D04：高风险确认绑定动作，而不是只读聊天文本

- 问题：“用户之前好像同意过”不能构成当前动作授权，关键词过宽也会误判疑问或否定。
- 决策：待确认状态绑定会话、动作类型、目标开度和 2 分钟 TTL；取消优先，确认必须是完整明确回复，并一次性消费。
- 放弃：模型自行根据历史判断 `confirmed=true`。
- 代价：确认期间会暂缓处理其他话题，换取授权语义清晰。
- 成功信号：“天气好吗？”、“不好”、“好吧，不要打开”均不会执行天窗。

## D05：确定性测试进 CI，模型行为评测独立运行

- 问题：把真实模型测试设为每次提交门禁会带来成本、密钥和随机失败；完全不测模型又看不到规划质量。
- 决策：参数、安全、授权、TTL、限流和评分规则用 Pytest/Vitest 固定；15 个三类模型任务在评测页或 Python CLI guarded live 运行并导出版本化报告。
- 放弃：把某一次 10/10 宣称为永久正确率。
- 代价：发布前需要主动运行并归档模型评测。
- 下一验证：扩展到 30–50 条，多轮重复后报告均值、方差、P95、失败类型和成本。

## D06：搜索充电站不等于授权导航

- 问题：用户可能只想比较候选站，自动导航属于超出意图的副作用。
- 决策：导航必须有明确语言意图、成功搜索前置，且目的地必须来自本轮候选。
- 放弃：只要识别到“充电”就自动导航。
- 代价：部分省略表达需要再问一次，换取副作用可控。
- 成功信号：“找顺路快充”只返回候选；“找顺路快充并导航”才修改目的地。
