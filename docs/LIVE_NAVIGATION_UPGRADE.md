# CabinGuard v4：真实导航与驾驶舱升级决策

> 文档状态：已实现首批 P0；日期：2026-09-14。本文记录公开项目调研、需求发散、优先级和真实能力边界。CabinGuard 的产品定义、座舱工具、策略、任务数据、实现代码与视觉界面均在本仓库独立完成；公开项目只用于研究行业问题与验证方法。

## 1. 为什么旧版不够

旧版 Agent Lab 已经证明了 Tool Calling、安全策略和工具轨迹，但用户看到的是固定充电站目录与坐标投影折线。它存在三个“意图—实现”缺口：

| 用户合理预期 | 旧版实现 | 影响 |
| --- | --- | --- |
| “导航到昌平区”能识别普通地址并算路 | `start_navigation` 仅接受固定充电站候选 | 普通导航被拒绝，核心体验断裂 |
| 地图能表达真实道路和路线 | SVG 对经纬度做简单投影 | 看起来像图表，不像座舱导航 |
| Agent 能处理复杂驾驶任务并解释决策 | 对话、状态和 Trace 分散在三个窄栏 | 信息密度低，规划能力难以被面试官看见 |

这不是“回复文案不好”，而是地点数据、算路能力和 HMI 信息架构没有闭环。

## 2. 外部研究带来的判断

### CAR-Bench

[CAR-Bench](https://github.com/CAR-bench/car-bench)重点衡量多轮工具 Agent 在不确定条件下的认识可靠性：工具是否存在、参数是否足够、策略是否允许、目标是否有歧义。公开仓库提供 58 个互联工具、19 类策略、254 个公开任务，并使用 Pass^k / Pass@k 观察重复运行的一致性。

对 CabinGuard 最有价值的不是复制工具数量，而是把“工具、政策、任务、状态、评分”做成一套可复核系统。CabinGuard 已有三类 15 任务评测和 Pass 指标，本次继续把地点候选、算路同意、外部失败与工具轨迹纳入同一信任模型。

### CAReful Agent

[CAReful Agent](https://github.com/gmsh/car-bench-exp-agent)展示了一种单 Agent 加确定性守卫链的方案：分别检查工具缺失、参数 Schema、策略、歧义和无依据完成声明。它支持一个重要判断：系统深度来自状态空间和可靠性约束，不来自把每个函数包装成一个 Agent。

### Cockpit Agent 与 VehiClaw

[Cockpit Agent](https://github.com/SuperdeMan/cockpit-agent)探索云边协同、多意图拆解、地图、记忆和多智能体座舱；[VehiClaw](https://github.com/nolanaechan/VehiClaw)强调语音优先、导航跳转、车辆上下文、主动服务和记忆。它们说明座舱产品需要把自然语言、位置、路线、车辆状态和服务建议组合起来，而不是停留在单轮问答。

本项目没有复制上述项目的代码或命名体系。CabinGuard 选择保留一个任务 Agent，通过 10 个严格工具、会话级候选绑定、确定性策略和可视化 Trace 增加任务复杂度；这比为了简历标签拆出多个互不协作的 Agent 更容易验证。

## 3. 三个视角的功能发散

### 产品经理视角

1. **任意地点导航**：支持自然语言地点、地址、行政区和 POI，消除“只能导航到充电站”的断点。
2. **路线—能耗联合决策**：展示到达电量，低电量时建议沿途补能，而不是只显示距离。
3. **多意图任务编排**：如“导航去公司，空调 23 度，路上找快充”，并行识别目标，按依赖顺序执行。
4. **偏好与常用地点**：在获得明确同意后保存家、公司、空调偏好；支持查看和删除。
5. **主动服务**：结合电量、天气、ETA 主动建议充电、除雾或提前调温，并控制提示频率。

### 设计师视角

1. **地图主画布**：真实道路图占据视觉中心，路线、起终点和状态覆盖在地图上。
2. **驾驶态信息分层**：第一层为 ETA、下一动作和风险，第二层为备选路线，第三层为开发 Trace。
3. **对话/轨迹/策略三态面板**：避免页面三列都很窄，并让面试演示可以一键切换证据。
4. **授权可理解**：定位按钮同时说明外部算路用途；不把浏览器权限弹窗包装成系统已默认授权。
5. **异常态诚实可见**：区分“未算路、检索失败、服务不可用、策略阻止”，禁止用假路线填空。

### 工程师视角

1. **地图供应商适配层**：地点检索和道路算路独立封装，未来可替换为高德或车企地图服务。
2. **候选 ID 绑定**：模型只看到候选 ID、名称和地址；精确坐标留在服务端会话，防止模型伪造目的地坐标。
3. **外部服务韧性**：超时、缓存、限流、可识别错误码和无假数据降级。
4. **路线数据契约**：统一距离、ETA、GeoJSON 点、步骤、备选路线、数据时间和预计到达电量。
5. **故障注入评测**：覆盖地图超时、空结果、重复地名、坐标越界和用户未同意外部算路。

## 5. 已实现的数据链路

```text
用户：“导航到昌平区政府”
        ↓
Agent 读取当前车辆状态
        ↓
search_places(query) → Nominatim 返回候选
        ↓
服务端保存候选坐标；模型只接收候选 ID、名称、地址
        ↓
plan_navigation(candidate_id) → 校验显式导航意图、读取前置、候选绑定、定位同意
        ↓
OSRM 返回道路距离、ETA、步骤、备选路线和 GeoJSON
        ↓
服务端估算到达电量并更新会话
        ↓
Leaflet + OpenStreetMap 呈现真实道路路线；Trace 呈现工具与策略证据
```

新增 Python 工具：

- `search_places`：按用户提交动作检索 1–5 个地点；24 小时进程内缓存，公共 Nominatim 请求间隔至少 1 秒。
- `plan_navigation`：只接受当前会话候选 ID，返回道路路线与能耗估算；浏览器真实坐标必须带外部算路同意。

地图供应商环境变量：

```dotenv
CABINGUARD_GEOCODER_URL=https://nominatim.openstreetmap.org/search
CABINGUARD_ROUTER_URL=https://router.project-osrm.org
CABINGUARD_NAV_COUNTRY_CODES=cn
CABINGUARD_MAP_USER_AGENT=CabinGuard/0.4 (+repository-url)
```

## 6. 不能夸大的边界

- 浏览器定位只能在 HTTPS 或 localhost 中由用户明确授予，网页不能替用户“默认允许一切地址权限”。
- “任意地点”指地理编码服务能够解析的公开地点，不代表能访问通讯录、收藏、家庭住址或封闭园区内部道路。
- 公共 Nominatim、OSRM 和 OpenStreetMap 瓦片适合本地低频演示，无可用性 SLA；禁止批量抓取、离线下载或高频自动补全。
- 当前没有实时交通、封路、车道级指引、导航播报定位跟随、高精地图，也未通过车规或功能安全认证。
- 车辆状态、车控、天气和固定充电站目录仍是模拟数据。真实地图不等于真实车辆控制。
- 到达电量使用当前“续航/电量”的线性估算，未建模速度、坡度、温度、空调和电池衰减，只能作为产品原型指标。

量产方向应使用有服务协议的地图提供商。中国大陆场景可在保持 `NavigationProvider` 契约的情况下替换为高德 Web Service；高德路线规划需要开发者 Key，JavaScript 地图还需要安全密钥。

## 7. 验证证据

- 当前 103 条 Python 测试：覆盖真实地点/道路协议、候选坐标隔离、定位同意、路线步骤完整性、OSRM 双端点容错和外部失败不伪造路线。
- 43 条 TypeScript 测试：继续验证语音追加、对话档案及前端回退工具的会话、安全和导航语义。
- 真实网络冒烟：默认北京模拟起点检索昌平区地点，底层 OSRM 直连返回约 45.9 km、38 分钟和 100 个简化道路点；结果随查询候选与公共地图数据变化，不作为固定断言。
- 真实 Agent 复合任务：“导航到昌平区政府，同时把空调调到23度并切换外循环”在 3 个模型轮次内执行 `get_climate_state → get_vehicle_state → search_places → set_climate → plan_navigation`，同时完成真实导航与座舱控制。
- UI 通过生产构建与浏览器视觉检查后再提交。
