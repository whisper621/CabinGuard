# CabinGuard：从单 Agent 到混合多 Agent 的演进决策

> **历史方案快照。** 本文用于保留架构取舍过程，旧工具/信号/测试数量不作为当前事实；请以 [CURRENT_STATUS](CURRENT_STATUS.md) 为准。

## 结论先行

CabinGuard v0.5 继续保持 **一个面向用户的 Orchestrator Agent + 多个确定性领域执行器** 是正确的，不应为了简历把它直接改名为“多 Agent”。

目前的单 Agent 并不等于“简单聊天机器人”：`AgentService` 执行多轮 Tool Calling，调用 14 个严格 Schema 工具；导航、座舱安全、VSS 约束、会话记忆分别由独立执行器实现。它已经足够构成 AI 产品经理、互联网产品经理的高质量作品集 MVP，也能作为智能座舱/具身方向的“可信执行原型”。

真正需要演进的是 **任务编排能力**，而不是 Agent 名称数量。推荐路线为：先实现可审计的任务图与逻辑领域模块，再在工具数量、上下文、并发和团队边界达到阈值后，将其中 2–3 个模块升级为有独立提示词、上下文和委托协议的 Domain Agent。

## 1. 当前事实：意图与实现核查

| 维度 | 项目意图 | 实现证据 | 结论 |
| --- | --- | --- | --- |
| 用户体验 | 一个统一的座舱助手 | `src/app/agent-lab/AgentLab.tsx` 只有一个对话入口 | 符合座舱低打扰交互 |
| 主编排 | 模型决定工具链，服务端掌握动作权 | `backend/cabinguard/agent.py` 中 `AgentService` 和最多 6 轮循环 | 已实现，且可观测 |
| 领域执行 | 导航、车控、记忆安全隔离 | `navigation.py`、`tools.py`、`memory.py`、`signals.py` 分别承载 | 是“模块化执行器”，不是多个 LLM Agent |
| 安全边界 | 模型不能绕过车辆约束 | `evaluate_write()` 和 5 条约束；75 条 Python 测试覆盖 | 已实现并有确定性证据 |
| 多 Agent | 文档没有声称已完成 | README 和技术报告明确标注单 Agent | 无“宣称多 Agent、代码只有一个”的失真 |

当前可准确描述为：

```text
用户 / 语音
    ↓
CabinGuard Orchestrator Agent（DeepSeek，多轮规划）
    ├── Navigation domain executor（地点、道路、隐私同意）
    ├── Cabin safety executor（HVAC、车身、VSS、约束）
    ├── Session memory executor（偏好、行程回执）
    └── Trace / Evaluation / HMI
```

这与“所有设备功能都再包一层 LLM Agent”相比，更安全、更低延迟，也更符合确定性车控的需要。

## 2. 什么时候真的值得拆 Domain Agent

满足下列任意两项，再将模块升级为独立 Domain Agent：

1. 工具达到约 25–30 个，主 Agent 出现选错工具、漏前置或上下文超长的问题。
2. 某领域需要独立的大型知识上下文，例如导航实时交通、车辆知识库、媒体版权目录或视觉场景摘要。
3. 可并行的子任务成为高频需求，例如“读车辆状态 + 查天气 + 搜 POI”，且并行能显著降低等待时间。
4. 不同团队维护不同能力，必须有独立版本、SLA、权限和回滚边界。
5. 某领域使用完全不同的模型或模态，例如视觉感知模型、离线端侧模型、语音模型。

在这之前，采用“一个模型 + 动态工具集 + 确定性服务”通常比多 Agent 更容易控制成本、延迟和安全。官方多 Agent 指引也将上下文管理、团队独立维护和并行化作为拆分动机，而非把每个 API 都包装为 Agent。

## 3. 三视角发散：15 个候选方向

### 产品经理视角

1. **跨域出行任务**：将舒适调节、POI 搜索、导航、补能和记忆组合为一条可验证用户旅程。
2. **任务图解释**：在执行前展示“将做什么、为什么、哪些需确认”，提升信任。
3. **多乘员权限**：主驾、乘客、儿童和访客拥有不同的设备控制范围。
4. **主动服务策略**：基于低电量、天气和日程提出建议，但绝不自动触发高风险动作。
5. **结果指标面板**：记录完成率、澄清率、拦截率、人工确认率、P95 延迟和每任务成本。

### 产品设计视角

1. **任务编排卡片**：将多步骤任务拆成可折叠、可取消的执行卡。
2. **授权分层可视化**：用直执、确认、禁止三种状态解释系统为什么执行或拒绝。
3. **行程中的渐进披露**：驾驶时只显示关键语音反馈，驻车后可展开完整 Trace。
4. **多域状态总览**：将空调、车身、导航、媒体和记忆状态按任务相关度浮现。
5. **失败恢复交互**：地图/设备不可用时给出安全替代路径，而不是只显示报错。

### 工程视角

1. **TaskPlan 编译器**：将一句话转成带依赖、权限、可并行标记的 Pydantic 任务图。
2. **Domain Manifest**：每个领域声明工具、输入输出、前置条件、SLA、权限和版本。
3. **选择性委托协议**：Orchestrator 将领域任务委托给受限上下文的 Domain Agent，并以结构化结果回收。
4. **WebSocket 信号播放器**：模拟 10 Hz VSS 变化、动作过渡、超时、冲突与回执。
5. **组合任务评测集**：新增跨域、多轮、中断、权限冲突和外部服务失败的轨迹测试。

## 4. Top 5 优先级

| 优先级 | 功能 | 为什么优先 | 要验证的假设 | 预计复杂度 |
| --- | --- | --- | --- | --- |
| P0 | TaskPlan + 任务图执行器 | 直接把“一个 Agent 会调多个工具”升级为可讲、可测的跨域编排能力 | 显式依赖图能降低工具顺序错误 | 中 |
| P0 | 组合任务评测集 | 项目是否优秀取决于复杂任务仍可验证，而非工具数量 | 新增 20–30 条组合用例可暴露真实缺口 | 中 |
| P1 | Domain Manifest + 逻辑领域模块 | 为日后多 Agent 留下接口，同时不增加 LLM 调用 | 模块元数据可减少提示词膨胀与文档漂移 | 中 |
| P1 | WebSocket VSS 信号播放器 | 显著增强具身/座舱岗位说服力 | 真实时间状态变化能验证冲突、超时和回执 | 高 |
| P1 | 多乘员权限与授权卡片 | 将“安全规则”升级为可产品化的权限系统 | 明确身份/座位权限可减少越权操作 | 中 |

## 5. 推荐的 v0.6 架构：混合式，而非强行多 LLM

```text
用户请求
  ↓
Orchestrator Agent
  ├─ 任务拆分 → TaskPlan（任务、依赖、权限、风险、并发性）
  ├─ Comfort Domain Module（确定性优先）
  ├─ Navigation & POI Domain Agent（需要检索/路线推理时才调用模型）
  ├─ Vehicle Safety Service（永远确定性，不是 Agent）
  ├─ Memory Domain Module（显式写入授权）
  └─ Result Synthesizer（汇总有依据的回执）
       ↓
Trace、任务图、状态更新、HMI 卡片、评测数据
```

### 为什么这样拆

- **Comfort / Safety 不应先拆成 LLM Agent。** 空调、车窗、座椅、儿童锁和后备箱是确定性设备控制，应直接走 Schema、权限和规则。
- **Navigation / POI 最适合先成为领域 Agent。** 它需要地点候选、路线偏好、隐私同意、外部失败恢复，并会继续扩展到实时交通、停车、餐饮评分等上下文。
- **Memory 先保持模块。** 当前会话偏好和行程回执规模小；只有发展为长期画像、隐私撤回、跨设备同步后才值得独立 Agent/服务。
- **视觉感知必须独立。** 未来接入摄像头时，先产出结构化事件（如儿童遗留、驾驶员疲劳、遮挡），再由 Orchestrator 决策；不要把原始视频直接塞进通用对话上下文。

## 6. 面试时怎么讲

推荐说法：

> CabinGuard 当前采用“一个用户可见的 Orchestrator Agent + 多个确定性领域执行器”的混合架构。原因是座舱车控具备高安全性和低延迟要求，不能把空调、车窗等简单动作都交给多个 LLM 推理。主 Agent 只负责理解、拆任务和调度；导航、座舱安全、记忆分别有独立执行边界。项目已用 14 个工具、25 个 VSS 对齐信号、5 条声明式约束和 114 条双栈自动测试验证这一闭环。下一阶段我会先落地 TaskPlan、组合任务评测和 WebSocket 信号流；当导航/POI 的上下文、工具量和并发需求达到阈值时，再将它升级为真正可委托的 Domain Agent。

不要说：

- “我已经做了 14 个 Agent。”
- “车控 Agent 直接控制真实车辆。”
- “多 Agent 一定比单 Agent 高级。”

## 7. 作品集判断

### 当前是否足够

- **AI 产品经理 / 互联网产品经理：足够作为主项目。** 已有完整问题定义、交互、后端、真实地图服务、安全机制、评测和可演示证据。
- **智能座舱产品经理：有竞争力，但需要补一层‘车辆信号流 + 任务图’会更强。** 现有 VSS 对齐和安全约束是亮点，车端实时性仍是缺口。
- **具身智能产品经理：可作为‘可信感知—规划—执行’原型，但不能替代真实机器人/视觉/仿真项目。** 补 WebSocket 信号流、事件感知与动作回执后更贴近该岗位。

### 决定优秀与否的最后三件事

1. 用 3 分钟现场演示一个跨域任务、一次安全拒绝和一次失败恢复。
2. 讲清楚为什么“车控是工具/服务而不是 LLM Agent”，并能用 Trace 和测试证明。
3. 补一份用户研究或可用性测试：至少 6–8 位访谈、5 位任务测试，记录完成率、理解成本与安全提示信任感。

## 8. 建议的 4 周落地节奏

| 周次 | 交付物 | 验收标准 |
| --- | --- | --- |
| 第 1 周 | `TaskPlan` Schema、依赖图、执行前预览 | 5 个组合任务可生成正确依赖与风险标签 |
| 第 2 周 | 20–30 条组合任务评测 + 报告页 | 可比较单工具与组合任务的通过率、轮次与延迟 |
| 第 3 周 | VSS WebSocket 信号播放器与动作回执 | 展示状态流、冲突、超时、取消和安全阻断 |
| 第 4 周 | 导航/POI 领域委托原型 + 用户测试 | 证明何时委托带来更少工具错误或更低延迟 |
