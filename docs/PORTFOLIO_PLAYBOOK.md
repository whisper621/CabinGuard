# CabinGuard 求职作品集讲述手册

## 一句话定位

CabinGuard 是一个面向智能座舱的可信任务 Agent MVP：让大模型负责理解与规划，让服务端工具层负责状态读取、安全校验、受控执行与结果核验。

## 招聘方应该看到的能力

| 产品能力 | 项目证据 |
| --- | --- |
| 问题定义 | 从“语音助手会回答”转向“任务是否安全、可验证地完成” |
| 用户与场景取舍 | 聚焦导航、舒适域、车身域、补能和会话连续性等高频任务 |
| AI 产品设计 | 区分确定性工作流与开放式 Tool Calling，并设计模型不可用回退 |
| 风险设计 | 5 条声明式约束、分级权限、导航显式授权和会话记忆写入授权 |
| 指标与评测 | 关键工具链、最终状态、澄清、越权行为、延迟和 Token |
| 跨职能落地 | PRD、交互页面、API、执行器、测试、CI 和评测报告形成闭环 |

## 四类岗位的讲述重点

### AI 产品经理

- 重点：为什么不能只靠 Prompt；如何在模型自治和确定性之间做分层。
- 决策：主页追求稳定复现，Agent Lab 观察自主 Tool Calling，硬规则统一放在应用执行层。
- 证据：14 个工具、25 个 VSS 对齐信号、最多 6 轮规划、真实地点/道路服务、无依据成功反馈拦截、模型行为评测。
- 避免：不要把 14 个工具说成 14 个 Agent，也不要声称训练了模型。

### 互联网产品经理

- 重点：用户目标、任务漏斗、失败恢复和可观测性。
- 漏斗：输入任务 → 正确理解 → 必要上下文齐全 → 允许执行 → 工具成功 → 用户收到可核验反馈。
- 指标：任务完成率、必要澄清命中率、安全拦截率、无依据成功反馈率、P95 延迟和单任务成本。
- 后续实验：比较“直接执行”“先解释风险”“解释并提供替代方案”对完成率与信任评分的影响。

### 具身智能产品经理

- 重点：把项目描述为轻量的“感知状态—任务规划—动作执行—反馈验证”原型。
- 已有证据：25 个 VSS 对齐信号构成感知状态；工具是动作接口；声明式约束和确认状态机是 Human-in-the-loop。
- 必须说明：没有真实传感器、机器人策略模型、仿真器或硬件闭环，当前不能证明运动控制能力。
- 下一步：把当前 VSS 对齐状态升级为 WebSocket 信号流，加入状态延迟、传感器冲突、动作超时和中断恢复。

### 智能座舱产品经理

- 重点：驾驶场景中的低打扰、安全优先、跨域任务和结果可核验。
- 亮点案例：高速开天窗不是简单拒绝，而是读取车速/天气、解释风噪、请求一次性确认并保留目标开度。
- 产品权衡：模拟数据保证演示稳定；真实上车前需要车端网关、权限、签名、幂等和审计。
- 已实现的延展：车窗、座椅、氛围灯、除霜、会话偏好和导航行程回执；后续做多乘员权限、驾驶分心、弱网降级和车云协同。

## 简历项目描述

> **CabinGuard｜可信智能座舱协同 Agent**  使用 Python、FastAPI、Pydantic、SQLite、WebSocket、Next.js 与 DeepSeek Tool Calling，将跨域需求编译为带依赖、风险、权限和工具白名单的 TaskPlan；设计 1 个主编排 Agent、1 个导航领域 Agent 边界与 4 个确定性服务，以四类乘员及设备/座位 ABAC、25 个 VSS 对齐信号、5 条声明式约束、状态版本和因果证据账本保障执行可信；接入 Nominatim/OSRM 真实地点与道路数据，搭建任务驾驶舱、场景仿真、执行追溯、24 个组合契约、15 个模型任务和 130 条双栈自动测试。

可拆成三条简历要点：

- 从车载助手“误执行、忽略上下文、无依据报成功”问题出发，定义导航、舒适、车身、补能和记忆任务及成功/安全指标，完成可交互 MVP。
- 设计“LLM 规划层 + 服务端可信工具层”，以 25 个 VSS 对齐信号和声明式规则约束 14 个工具的参数、前置、地图候选、风险动作与反馈。
- 构建 Python/FastAPI Agent API、TaskPlan、Policy Kernel、SQLite 证据账本与 WebSocket 时序信号流，并用 130 条双栈自动测试和 CI 固化关键安全及评分规则。

## 5 分钟演示脚本

1. 用“把空调调到 23 度”展示状态读取、参数化执行和 Trace。
2. 在任务驾驶舱切换访客/儿童角色展示 ABAC 拒绝，再到场景仿真注入高速/降雨事件，用“把天窗开一半”展示同一意图因环境变化而进入确认或阻止。
3. 输入“把主驾车窗打开一半，再开 2 挡座椅通风并把氛围灯调成紫色”，展示跨域组合工具链和页面状态回执。
4. 用“找一个顺路快充站”证明不会擅自导航，再用“找个顺路快充并导航”展示真实路线闭环。
5. 打开执行追溯沿 planId、taskId、策略与状态版本复盘；再到可靠性评测展示 24 条组合契约和模型轨迹失败原因。

## 高频追问与诚实回答

**为什么要把用户体验与验证页面分开？** 任务驾驶舱只承载用户任务；场景仿真、执行追溯、可靠性评测和技术架构分别提供环境、证据、质量与运行时边界，避免把用户路径做成研发控制台。

**为什么不直接接真实车辆？** MVP 先验证交互、安全边界和评测方法。真实接入会引入身份、车端签名、幂等、网关与法规问题，必须单独设计。

**大模型有什么不可替代性？** 对自然语言、多意图和上下文的理解与规划有价值；确定性安全规则和执行结果不交给模型决定。

**怎么证明不是 Demo 拼装？** 展示服务端执行器、否定/模糊确认测试、导航越权测试、CI，以及一次失败评测如何推动前置条件升级。

## 下一轮产品升级优先级

1. P0：任务幂等键、可取消后台任务和异步动作回执。
2. P1：把 VSS 对齐状态接入 WebSocket 车辆信号流，演示异步变化和冲突。
3. P1：完成 8–12 位目标用户访谈和 5 位可用性测试，验证澄清、风险说明与信任感。
4. P1：扩展 30–50 条模型用例，报告多轮均值、方差、P95 和单任务成本。
5. P2：多乘员权限、账号级可撤回记忆、弱网降级与中断恢复。

任何尚未完成的研究、真实接入或线上指标必须标记为计划，不能包装成已有结果。
