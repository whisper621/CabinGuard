# CabinGuard 求职作品集讲述手册

## 一句话定位

CabinGuard 是一个面向智能座舱的可信任务 Agent MVP：让大模型负责理解与规划，让服务端工具层负责状态读取、安全校验、真实执行与结果核验。

## 招聘方应该看到的能力

| 产品能力 | 项目证据 |
| --- | --- |
| 问题定义 | 从“语音助手会回答”转向“任务是否安全、可验证地完成” |
| 用户与场景取舍 | 聚焦舒适度、天窗、补能、后备箱四类高频且差异明显的任务 |
| AI 产品设计 | 区分确定性工作流与开放式 Tool Calling，并设计模型不可用回退 |
| 风险设计 | 降雨阻止、高速确认、行驶中后备箱阻止、导航显式授权 |
| 指标与评测 | 关键工具链、最终状态、澄清、越权行为、延迟和 Token |
| 跨职能落地 | PRD、交互页面、API、执行器、测试、CI 和评测报告形成闭环 |

## 四类岗位的讲述重点

### AI 产品经理

- 重点：为什么不能只靠 Prompt；如何在模型自治和确定性之间做分层。
- 决策：主页追求稳定复现，Agent Lab 观察自主 Tool Calling，硬规则统一放在应用执行层。
- 证据：8 个工具、最多 6 轮规划、无依据成功反馈拦截、模型行为评测。
- 避免：不要把 8 个工具说成 8 个 Agent，也不要声称训练了模型。

### 互联网产品经理

- 重点：用户目标、任务漏斗、失败恢复和可观测性。
- 漏斗：输入任务 → 正确理解 → 必要上下文齐全 → 允许执行 → 工具成功 → 用户收到可核验反馈。
- 指标：任务完成率、必要澄清命中率、安全拦截率、无依据成功反馈率、P95 延迟和单任务成本。
- 后续实验：比较“直接执行”“先解释风险”“解释并提供替代方案”对完成率与信任评分的影响。

### 具身智能产品经理

- 重点：把项目描述为轻量的“感知状态—任务规划—动作执行—反馈验证”原型。
- 已有证据：车速、天气、电量和舱温是环境状态；工具是动作接口；确认状态机是 Human-in-the-loop。
- 必须说明：没有真实传感器、机器人策略模型、仿真器或硬件闭环，当前不能证明运动控制能力。
- 下一步：接入 VSS/WebSocket 车辆模拟器，加入状态延迟、传感器冲突、动作超时和中断恢复。

### 智能座舱产品经理

- 重点：驾驶场景中的低打扰、安全优先、跨域任务和结果可核验。
- 亮点案例：高速开天窗不是简单拒绝，而是读取车速/天气、解释风噪、请求一次性确认并保留目标开度。
- 产品权衡：模拟数据保证演示稳定；真实上车前需要车端网关、权限、签名、幂等和审计。
- 可延展方向：用户偏好记忆、多乘员权限、驾驶分心指标、弱网降级和车云协同。

## 简历项目描述

> **CabinGuard｜可信智能座舱任务 Agent**  使用 Python、FastAPI、Pydantic、Next.js 与 DeepSeek Tool Calling 实现智能座舱任务 MVP，设计车况、天气、空调、天窗、补能搜索、导航和后备箱等 8 个工具，跑通“意图理解—状态读取—安全校验—工具执行—结果核验”闭环。将模型限制在规划层，在 Python 服务端实现严格参数校验、读取前置、高速天窗一次性确认、降雨/行驶风险阻止、导航显式授权与结果溯源；搭建 10 类模型行为评测、51 条 Python 测试、35 条 TypeScript 兼容测试和 CI。

可拆成三条简历要点：

- 从车载助手“误执行、忽略上下文、无依据报成功”问题出发，定义 4 类核心任务和 5 个成功/安全指标，完成可交互 MVP。
- 设计“LLM 规划层 + 服务端可信工具层”，以硬规则约束 8 个工具的参数、前置状态、风险动作和结果反馈。
- 构建 Python/FastAPI Agent API、Agent Trace 与回归评测台，记录工具链、最终状态、Token、轮次、延迟和失败原因，并用 86 条双栈自动测试与 CI 固化关键安全规则。

## 5 分钟演示脚本

1. 用“把空调调到 23 度”展示状态读取、参数化执行和 Trace。
2. 在 Agent Lab 切换高速/降雨场景，用“把天窗开一半”展示同一意图因环境不同而进入确认或阻止；高速场景先输入“天气好吗？”证明不会误确认，再输入“确认继续”完成动作。
3. 用“找一个顺路快充站”证明不会擅自导航，再用“找个顺路快充并导航”展示多工具闭环。
4. 用行驶场景打开后备箱，展示模型无法绕过执行器硬规则。
5. 打开评测页解释关键工具有序链、失败原因、延迟和 Token，而不是只展示一次成功对话。

## 高频追问与诚实回答

**为什么有两条 Agent 链路？** 主页用于稳定复现产品策略，Agent Lab 用于验证模型自主选择工具；两者服务于不同实验目标。

**为什么不直接接真实车辆？** MVP 先验证交互、安全边界和评测方法。真实接入会引入身份、车端签名、幂等、网关与法规问题，必须单独设计。

**大模型有什么不可替代性？** 对自然语言、多意图和上下文的理解与规划有价值；确定性安全规则和执行结果不交给模型决定。

**怎么证明不是 Demo 拼装？** 展示服务端执行器、否定/模糊确认测试、导航越权测试、CI，以及一次失败评测如何推动前置条件升级。

## 下一轮产品升级优先级

1. P0：API 两轮确认集成测试、请求幂等键、保存一份可复核的评测 JSON。
2. P1：接入 VSS/WebSocket 车辆模拟器，演示异步状态变化和动作回执。
3. P1：完成 8–12 位目标用户访谈和 5 位可用性测试，验证澄清、风险说明与信任感。
4. P1：扩展 30–50 条模型用例，报告多轮均值、方差、P95 和单任务成本。
5. P2：多乘员权限、偏好记忆、弱网降级与中断恢复。

任何尚未完成的研究、真实接入或线上指标必须标记为计划，不能包装成已有结果。
