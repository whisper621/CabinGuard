# CabinGuard 求职作品集讲述手册

## 一句话定位

CabinGuard 是一个面向智能座舱的可信任务 Agent MVP：让大模型负责理解与规划，让服务端工具层负责状态读取、安全校验、受控执行与结果核验。

## 招聘方应该看到的能力

| 产品能力 | 项目证据 |
| --- | --- |
| 问题定义 | 从“语音助手会回答”转向“任务是否安全、可验证地完成” |
| 用户与场景取舍 | 聚焦导航、舒适域、车身域、补能和会话连续性等高频任务 |
| AI 产品设计 | 区分确定性工作流与开放式 Tool Calling，并设计模型不可用回退 |
| 风险设计 | 9 条声明式约束、分级权限、导航显式授权、幂等/冲突/取消/超时和长期偏好单独授权 |
| 指标与评测 | 关键工具链、最终状态、澄清、越权行为、延迟和 Token |
| 跨职能落地 | PRD、交互页面、API、执行器、测试、CI 和评测报告形成闭环 |

## 四类岗位的讲述重点

### AI 产品经理

- 重点：为什么不能只靠 Prompt；如何在模型自治和确定性之间做分层。
- 决策：地图优先主页就是统一 Agent 工作台；确定性 TaskPlan/混合路由保证常用任务可复现，大模型在同一 Python 链路内处理开放式理解和工具选择，硬规则统一放在服务端执行层。
- 证据：23 个工具、41 个 VSS 对齐信号、最多 6 轮模型工具选择、真实地点/道路/补能 POI、无依据成功反馈拦截、首轮 50×3 模型基线与修复后问题集定向复测。
- 避免：不要把 23 个工具说成 23 个 Agent，不要说 TaskPlan 由模型生成，也不要把“首轮 113/150 + 定向 12/12”包装成“修复后全量通过”。

### 互联网产品经理

- 重点：用户目标、任务漏斗、失败恢复和可观测性。
- 漏斗：输入任务 → 正确理解 → 必要上下文齐全 → 允许执行 → 工具成功 → 用户收到可核验反馈。
- 指标：任务完成率、必要澄清命中率、安全拦截率、无依据成功反馈率、P95 延迟和单任务成本。
- 后续实验：比较“直接执行”“先解释风险”“解释并提供替代方案”对完成率与信任评分的影响。

### 具身智能产品经理

- 重点：把项目描述为轻量的“感知状态—任务规划—动作执行—反馈验证”原型。
- 已有证据：41 个 VSS 对齐信号构成结构化状态；工具是动作接口；声明式约束、主动建议接受和确认状态机形成 Human-in-the-loop。
- 必须说明：没有真实传感器、机器人策略模型、仿真器或硬件闭环，当前不能证明运动控制能力。
- 本轮边界：按项目范围不实施 ROS2、KUKSA、机器人或真实硬件改造；申请具身岗位时只能强调安全任务系统的可迁移方法，不能包装为具身控制项目。

### 智能座舱产品经理

- 重点：驾驶场景中的低打扰、安全优先、跨域任务和结果可核验。
- 亮点案例：高速开天窗不是简单拒绝，而是读取车速/天气、解释风噪、请求一次性确认并保留目标开度。
- 产品权衡：模拟数据保证演示稳定；请求级幂等与审计已在原型中实现，真实上车仍需要车端网关、可信身份、签名和跨服务补偿。
- 已实现的延展：车窗、座椅、氛围灯、除霜、四类乘员权限、会话偏好和导航行程回执；后续做驾驶分心、弱网降级和车云协同。

## 简历项目描述

> **CabinGuard｜可信智能座舱协同 Agent** 使用 Python、FastAPI、Pydantic、SQLite、WebSocket、Next.js 与 DeepSeek Tool Calling，通过确定性编译器把跨域目标转换为带依赖、风险、权限和工具白名单的 TaskPlan，再让模型在边界内选择工具；设计 1 个主编排边界、导航/媒体 2 个领域边界与 5 个确定性服务，以四类乘员 ABAC、41 个 VSS 对齐信号、9 条声明式约束、请求生命周期和因果证据账本保障执行可信；接入 Nominatim/OSRM/Overpass 公共数据与音乐试听，构建地图优先 Driver Mode、独立 Validation Mode、8 组体验场景、200 条确定性合同、50 个模型语义任务和 385 条双栈自动测试。

可拆成三条简历要点：

- 从车载助手“误执行、忽略上下文、无依据报成功”问题出发，定义导航、舒适、车身、补能和记忆任务及成功/安全指标，完成可交互 MVP。
- 设计“可信 TaskPlan 编译器 + 有边界的 LLM 工具选择 + 服务端确定性执行”，以 41 个 VSS 对齐信号和 9 条声明式规则约束 23 个工具的参数、前置、地图候选、风险动作与反馈。
- 构建 Python/FastAPI Agent API、请求幂等/冲突/取消/超时、可撤销 TTL 偏好、主动建议、Policy Kernel、SQLite 证据账本与 WebSocket 时序信号流，并用 385 条双栈自动测试和 CI 固化关键规则。

## 5 分钟演示脚本

1. 用“把空调调到 23 度”展示状态读取、参数化执行和 Trace。
2. 在智能座舱首页切换访客/儿童角色展示 ABAC 拒绝，再到验证中心注入高速/降雨事件，用“把天窗开一半”展示同一意图因环境变化而进入确认或阻止。
3. 输入“把主驾车窗打开一半，再开 2 挡座椅通风并把氛围灯调成紫色”，展示跨域组合工具链和页面状态回执。
4. 用“找一个顺路快充站”证明不会擅自导航，再用“找个顺路快充并导航”展示真实路线闭环。
5. 在验证中心切换“执行追溯”，沿 planId、taskId、策略与状态版本复盘；再切换“可靠性评测”展示 200 条场景矩阵、24 条组合契约、50 条模型语义任务和轨迹失败原因。

## 高频追问与诚实回答

**为什么产品只保留一个主页面？** 用户只需要一个统一座舱助手，因此大地图、任务图、角色权限和执行回执都进入首页；场景注入、证据与评测属于研发验证能力，统一放在验证中心，避免多个“主控台”互相竞争。

**为什么不直接接真实车辆？** MVP 先验证交互、安全边界和评测方法。真实接入会引入身份、车端签名、幂等、网关与法规问题，必须单独设计。

**大模型有什么不可替代性？** 对自然语言、多意图和上下文的理解与规划有价值；确定性安全规则和执行结果不交给模型决定。

**怎么证明不是 Demo 拼装？** 展示服务端执行器、否定/模糊确认测试、导航越权测试、CI，以及一次失败评测如何推动前置条件升级。
