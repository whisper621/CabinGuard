# CabinGuard 产品需求文档（MVP）

## 1. 产品问题

当前车载语音助手常能理解一句话，却容易在执行阶段出现三个问题：用户表达模糊时直接猜测；忽略车速、天气等上下文；工具没有成功仍反馈“已完成”。这些问题会降低信任，在驾驶场景还可能带来安全风险。

CabinGuard 验证的核心假设是：如果 Agent 在动作前主动读取上下文、对高风险或模糊请求进行澄清，并用工具返回值核验结果，用户会更愿意把跨系统任务交给它完成。

## 2. 目标用户与场景

目标用户为新能源车主和经常使用座舱语音功能的驾驶者。首期选择四类高频、可验证且差异明显的场景：

| 场景 | 用户目标 | 关键难点 |
| --- | --- | --- |
| 舒适度调节 | 快速获得合适的温度和空气状态 | “舒服一点”缺少明确参数 |
| 天窗控制 | 通风或改善采光 | 需要结合车速、天气和确认状态 |
| 补能导航 | 在当前路线中选择合适的快充站 | 需要组合电量、续航、绕行和空闲桩 |
| 后备箱控制 | 开启或关闭尾门 | 行驶状态下必须拦截 |

## 3. MVP 目标

- 跑通从自然语言请求到工具执行和结果反馈的完整链路。
- 让所有执行动作都能追溯输入、输出和状态。
- 在高风险场景执行前完成状态校验和明确确认。
- 形成可重复运行的测试集，而不是依赖一次成功演示。

本期不接入真实车控、地图和充电平台，也不训练模型。

## 4. 核心需求

### 4.1 意图与槽位

系统识别座舱调节、天窗、补能、后备箱和车辆状态查询。用户给出明确温度或开度时直接提取；“舒服一点”等缺少关键条件的请求进入澄清流程。

### 4.2 上下文读取

动作执行前读取所需状态。天窗需要车速和天气；补能需要电量、续航和当前路线；空调调节需要当前温度与循环模式。

### 4.3 风险控制

- 车速不低于 80 km/h 时，开启天窗必须二次确认。
- 降雨概率不低于 50% 时，阻止开启天窗并提供通风替代方案。
- 非驻车状态下阻止开启后备箱。
- 未接入能力或工具未成功时，明确说明未完成。

### 4.4 执行反馈

反馈包含执行对象、关键参数和结果。推荐充电站时说明选择依据；被拦截时说明状态、规则和下一步可行条件。

### 4.5 可观测性

记录工具名称、输入、输出、执行状态和时间，展示任务完成、澄清、安全拦截和工具调用指标。

## 5. 成功指标

| 指标 | 定义 | MVP 目标 |
| --- | --- | --- |
| 任务完成率 | 正确完成的可执行任务 / 全部可执行任务 | ≥ 85% |
| 工具选择正确率 | 正确工具序列 / 全部任务 | ≥ 90% |
| 高风险拦截率 | 被正确阻止或确认的风险动作 / 风险请求 | 100% |
| 无依据成功反馈率 | 工具未成功却宣称完成的次数 / 全部反馈 | 0% |
| 必要澄清命中率 | 正确触发澄清的模糊任务 / 模糊任务 | ≥ 90% |

## 6. 后续路线

下一阶段应接入车机模拟器或标准化信号层，增加连续多轮任务、用户偏好记忆和中断恢复；之后再接地图、充电平台和真实车控沙箱，开展延迟、网络异常、权限和驾驶分心测试。
