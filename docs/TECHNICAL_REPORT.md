# CabinGuard 技术原理与项目说明

## 1. 项目定位与结论

CabinGuard 是一个面向智能座舱场景的可信任务 Agent MVP。它验证的不是“能否聊天”，而是把自然语言目标安全地转为可观察、可校验的工具调用：

```text
用户请求 → 意图理解/任务规划 → 上下文读取 → 风险判断或澄清
        → 服务端工具执行 → 状态更新 → 基于工具结果的反馈
```

当前版本已经具备可展示、可交互、可复测的 MVP 闭环，适合作为 AI 产品经理的作品集项目；它不是已接入真实车辆、地图、充电网络或车端网关的生产系统。

最准确的项目表述是：**单 Agent、多工具调用、服务端安全约束的智能座舱任务系统**。不要将其描述为多智能体系统，也不要称为真实车辆控制平台。

## 2. 核心产品实现

CabinGuard 围绕可信智能座舱任务闭环完成了以下核心产品实现：

- 智能座舱业务场景、交互界面和模拟车辆状态；
- DeepSeek 意图解析接口及 DeepSeek 多轮 Tool Calling Agent；
- 8 个座舱领域工具及其模拟执行器；
- 天窗、后备箱、补能等安全与前置条件；
- Agent Lab 调用轨迹展示；
- 10 条回归用例及 JSON 报告导出；
- PRD、架构说明和评测记录。

仓库仅保留与 CabinGuard 产品链路有关的 `cabinPilotAgent` 及实时语音基础设施。第三方组件和许可统一记录在根目录 `THIRD_PARTY_NOTICES.md`，不与核心产品能力混记。

## 3. 技术栈

| 层级 | 技术与职责 |
| --- | --- |
| 前端 | Next.js 16 App Router、React 19、TypeScript、Tailwind CSS，承载主页、Agent Lab 和评测页 |
| 模型服务 | DeepSeek Chat Completions 的结构化意图解析与函数调用；可选 OpenAI Realtime API 语音会话 |
| Agent 框架 | `@openai/agents` 的 RealtimeAgent 与工具定义，用于可选 Realtime 语音模式 |
| 服务端通信 | Next.js Route Handlers、Undici；DeepSeek 密钥只在服务端读取 |
| 运行状态 | 主页使用 React 内存状态；Agent Lab 使用 30 分钟有效的服务端内存会话；当前没有数据库、Redis 或持久化日志 |
| 语音能力 | 浏览器 Speech Recognition 做中文语音输入，Speech Synthesis 做结果播报；Realtime 语音是独立可选入口 |

## 4. 三条运行链路

### 4.1 主页：稳定演示链路

主页 `CabinDemo.tsx` 的设计目标是保证面试演示稳定。DeepSeek 只负责把自然语言解析为有限意图和槽位：`sunroof`、`charging`、`climate`、`trunk`、`status`、`unknown`。前端随后使用确定性工作流选择工具顺序、处理澄清、更新模拟状态并展示工具轨迹。

例如“车里有点闷，帮我把天窗开一半”的处理是：

1. DeepSeek 尝试识别“天窗”和目标开度；解析失败时使用本地正则兜底。
2. 前端读取模拟车速和天气。
3. 若降雨概率不低于 50%，直接阻止打开；若车速不低于 80 km/h，进入二次确认状态。
4. 用户确认后才更新天窗和遮阳帘状态。
5. 页面同时记录工具输入、输出、状态、任务完成率、澄清次数、安全保护次数和工具调用量。

这条链路的优点是即使 DeepSeek 不可用，核心场景也能通过本地规则展示；它本质上是“LLM 增强理解 + 确定性执行”，不是开放式 Agent 自主规划。

### 4.2 Agent Lab：DeepSeek 多轮 Tool Calling 链路

`/agent-lab` 是项目最能说明 Agent 能力的入口。浏览器先向 `/api/cabin/session` 创建服务端演示会话，后续只提交会话 ID、用户请求及最近 10 条对话历史。服务端把系统提示词、8 个函数 Schema 和用户消息发送给 DeepSeek；模型自主选择函数，服务端从会话读取状态、执行函数并写回会话，再把结果作为 `tool` 消息回传模型。

```text
浏览器
  │ 文本、有限会话历史、会话 ID
  ▼
Next.js /api/cabin/session → /api/deepseek/agent
  │ 系统提示词 + 8 个函数 Schema
  ▼
DeepSeek 模型
  │ tool_calls
  ▼
服务端工具执行器
  │ Zod 校验参数、执行前置与安全规则、更新模拟状态、生成 Trace
  └──────── 工具结果回传 DeepSeek ────────┘
  ▼
最终回复 + 最新状态 + 调用轨迹 + 模型轮次/Token/延迟
```

单个请求最多执行 6 个模型轮次；单轮模型请求失败时服务端最多重试 3 次，前端 Agent Lab 和评测页在收到 502 时会额外重试整条请求 1 次。这些限制用于避免无限工具循环、外部网络瞬断和异常成本。

### 4.3 OpenAI Realtime：可选语音链路

`/realtime?agentConfig=cabinPilot` 使用 OpenAI Realtime Agents SDK。浏览器先向 `/api/session` 获取短期 client secret，再建立实时语音会话；用户可文字输入、语音输入、Push-to-Talk 和下载录音。

该入口同样挂载 `cabinPilotAgent` 和座舱工具，但它与 DeepSeek Agent Lab 是两条独立实现：

- Realtime 工具 Schema 使用英文枚举，如 `inside/outside`、`high_speed_confirmed`；
- DeepSeek 工具 Schema 使用中文枚举，如“内循环/外循环”、`confirmed`；
- 两条链路都使用本地模拟数据，但共享的安全语义并非同一个服务端工具模块。

当前环境没有配置可用的 `OPENAI_API_KEY`，因此 Realtime 页面会正常打开，但会提示未启用，`/api/session` 返回 503。不能把 Realtime 语音功能写为“已完成实测”。

## 5. Agent 的工具系统

核心产品是 1 个 `cabinPilotAgent`。它能够调用以下 8 个工具：

| 工具 | 输入 | 返回/状态改变 | 业务目的与约束 |
| --- | --- | --- | --- |
| `get_vehicle_state` | 无 | 车速、挡位、电量、续航、路线、目的地 | 车辆动作和补能前置读取 |
| `get_weather` | 当前位置 | 天气、降雨概率 | 打开天窗前置读取 |
| `get_climate_state` | 无 | 车内温度、设定温度、风量、循环模式 | 调节空调前置读取 |
| `set_climate` | 温度、风量、循环模式 | 更新空调模拟状态 | DeepSeek 路径限制温度 16–30℃、风量 1–5 档 |
| `search_charging_stations` | 是否顺路、最大绕行 | 固定候选站、距离、绕行、空闲桩、到站电量 | DeepSeek 路径强制先读取车辆状态 |
| `start_navigation` | 目的地 | 更新目的地、返回预计到达时间 | 仅在用户明确要求导航时调用 |
| `control_sunroof` | 开度、确认状态 | 更新天窗/遮阳帘，或返回阻止原因 | 降雨阻止；高速必须确认 |
| `control_trunk` | 开/关 | 返回执行或阻止结果 | 行驶中不允许开启 |

所有工具调用都会产生 `Trace`：工具名称、模型参数、工具输出和 `success/blocked` 状态。Agent Lab 把 Trace 展示给用户，评测页也会读取同一字段判断工具链是否符合预期。

## 6. 可信性与安全设计

项目的核心设计是把模型视为“不可信的规划层”，把服务端工具视为“最终动作边界”。模型可以建议调用什么工具和传什么参数，但不能直接修改车辆状态，也不能绕过工具层反馈成功。

### 已实现的软约束：系统提示词

- 调空调前先读取空调状态；
- 打开天窗前先读取车速与天气；
- 补能前先读取车辆电量、续航和路线；
- 高速天窗需要说明风险并得到明确确认；
- 模糊请求优先澄清；
- 未接入能力不能假称完成；
- 只有工具返回 `executed=true` 或 `navigation_started=true` 才能说任务完成。

### 已实现的硬约束：服务端工具执行器

- 所有工具参数使用 Zod 严格校验，非法类型、范围、枚举和多余字段不会被静默纠正为成功；
- `set_climate`、`search_charging_stations`、`control_sunroof` 和后备箱开启分别强制校验所需的状态读取前置；
- `control_sunroof` 在降雨概率不低于 50% 时拒绝打开；在车速不低于 80 km/h 且 `confirmed !== true` 时拒绝打开；
- `control_trunk` 在车速大于 0 时拒绝打开；
- `start_navigation` 同时校验用户明确导航意图、搜索前置和本轮候选目的地；
- 最终回复没有成功工具副作用作为依据时，服务端会替换无依据的完成表述；
- 模型最大 6 轮，服务端调用 DeepSeek 最多 3 次有限重试。

这种“提示词负责引导、工具层负责最终拦截”的分层是项目最值得面试时说明的技术设计。

## 7. 模拟数据与状态管理

当前车辆状态、天气、充电站、路线和导航结果都是模拟数据。初始状态包括：82 km/h、D 挡、38% 电量、176 km 续航、26.5℃车内温度、20% 降雨概率，以及两座固定的顺路充电站。Agent Lab 会为每位使用者创建 30 分钟有效的服务端演示会话，并提供默认、降雨和行驶三种预置场景。

状态的流向是：

- 主页：状态仅在 React 内存中更新；刷新页面即重置。
- Agent Lab：浏览器仅提交会话 ID，服务端读取并更新会话状态，前端以返回状态刷新 React State。
- Realtime：`cabinPilot.ts` 内另有模块级 `demoState`。

因此当前项目没有真实 CAN 总线、车端控制器、地图 API、充电站 API、用户账户、数据库或审计数据仓库。它能够证明工具编排和安全交互设计，不能证明真实设备接入能力。

### 已有评测机制

评测页内置 10 条回归用例，调用的是真实 `/api/deepseek/agent` 接口，而非静态结果。它检查：

- 工具是否被调用；
- 禁止工具是否没有被调用；
- 最终模拟车辆状态是否正确；
- 是否触发了澄清或风险说明；
- 是否出现未请求导航却更新目的地等越权行为；

项目已经加入 Vitest 和 CI，用于固定不依赖外部模型的确定性安全规则。评测页仍属于需要 DeepSeek 密钥、存在成本与非确定性的 guarded live evaluation，不等同于完全可重复的单元测试。

## 9. 当前问题与生产化差距

### 必须如实说明的边界

1. **不是真实车控。** 当前车辆状态由服务端内存会话模拟；生产系统必须从可信车端网关或后端状态服务读取。
2. **只有演示级限流，没有身份认证。** 当前 DeepSeek Agent 路由按来源提供内存窗口限流，但没有用户身份、配额、持久化预算或分布式限流，公开部署仍有 API 成本和滥用风险。
3. **没有持久化。** 会话、状态和 Trace 不写入数据库，刷新后会丢失；评测报告仅下载到本地。
4. **Realtime 尚未启用验证。** 当前只有 DeepSeek 主链路可实际演示。
5. **模型行为评测尚未成为自动门禁。** 确定性规则已有 35 条 Vitest 测试与 CI；10 类模型行为仍需从页面运行并人工保存报告。
6. **跨链路参数不完全一致。** DeepSeek 空调风量为 1–5 档，Realtime 为 1–7 档；高速确认字段分别为 `confirmed` 与 `high_speed_confirmed`。后续接入真实后端前应统一契约。
7. **确认状态仍不是生产级授权。** 高速天窗确认已绑定会话、动作参数和 2 分钟有效期；生产环境仍应绑定任务 ID、车端签名、用户身份和审计记录。
8. **文案仍有语义歧义。** 天窗成功路径返回 `sunshade_percent: 100`，但模型曾描述为“遮阳帘保持全闭”；应在产品定义中统一百分比代表“开度”还是“闭合度”，并由前端模板化结果避免模型自行表述。
这些问题不影响把项目作为作品集 MVP 展示，但意味着它目前不能称为“生产级智能座舱系统”。

## 12. 60 秒技术讲述顺序

“我把 CabinGuard 做成了一个智能座舱可信任务 Agent，而不是单纯聊天机器人。核心逻辑是把模型放在任务规划层，把实际动作留给服务端工具层：模型先判断用户意图，再读取车速、天气、电量或空调状态，满足条件才允许执行。比如高速开天窗时，首次工具调用会创建服务端待确认动作，只有用户在同一会话内明确确认才会恢复执行；降雨概率超过 50% 或车辆行驶中打开后备箱则由工具层直接阻止。项目一共设计了 8 个工具，支持空调、天窗、补能搜索与导航、后备箱和车辆状态查询。我还用 DeepSeek 实现了多轮函数调用，所有工具参数、返回结果和拦截原因都会被记录到调用轨迹，并构建了 10 条回归用例验证任务完成、澄清和安全约束。”
