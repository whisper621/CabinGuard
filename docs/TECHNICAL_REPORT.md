# CabinGuard 技术原理与项目说明

## 1. 项目定位与结论

CabinGuard 是一个面向智能座舱场景的可信任务 Agent MVP。它验证的不是“能否聊天”，而是把自然语言目标安全地转为可观察、可校验的工具调用：

```text
用户请求 → 意图理解/任务规划 → 上下文读取 → 风险判断或澄清
        → 服务端工具执行 → 状态更新 → 基于工具结果的反馈
```

当前版本已经具备可展示、可交互、可复测的 MVP 闭环，并接入低频演示用的真实地点与道路数据，适合作为 AI 产品经理的作品集项目；它不是已接入真实车辆、实时交通、充电网络或车端网关的生产系统。

最准确的项目表述是：**单 Agent、多工具调用、服务端安全约束的智能座舱任务系统**。不要将其描述为多智能体系统，也不要称为真实车辆控制平台。

## 2. 核心产品实现

CabinGuard 围绕可信智能座舱任务闭环完成了以下核心产品实现：

- 智能座舱业务场景、交互界面和模拟车辆状态；
- DeepSeek 意图解析接口及 DeepSeek 多轮 Tool Calling Agent；
- 14 个座舱领域工具、模拟车控执行器、会话记忆执行器与外部地图适配器；
- 25 个 VSS 对齐信号，以及天窗、车窗、后备箱、空调等 5 条声明式约束；
- Agent Lab 调用轨迹与座舱状态展示、System Lab 运行时架构控制台；
- 15 个三类可靠性任务、Python 五维评分、一致性指标及 JSON 报告导出；
- PRD、架构说明和评测记录。

仓库仅保留与 CabinGuard 产品链路有关的 `cabinPilotAgent` 及实时语音基础设施。第三方组件和许可统一记录在根目录 `THIRD_PARTY_NOTICES.md`，不与核心产品能力混记。

## 4. 三条运行链路

### 4.1 主页：稳定演示链路

主页 `CabinDemo.tsx` 的设计目标是保证面试演示稳定。DeepSeek 只负责把自然语言解析为有限意图和槽位：`sunroof`、`charging`、`climate`、`trunk`、`status`、`unknown`。前端随后使用确定性工作流选择工具顺序、处理澄清、更新模拟状态并展示工具轨迹。

例如“车里有点闷，帮我把天窗开一半”的处理是：

1. DeepSeek 尝试识别“天窗”和目标开度；解析失败时使用本地正则兜底。
2. 前端读取模拟车速和天气。
3. 若降雨概率不低于 50%，直接阻止打开；若车速不低于 80 km/h，进入二次确认状态。
4. 用户确认后才更新天窗和遮阳帘状态。
5. 页面同时记录工具输入、输出、状态、任务完成率、澄清次数、安全保护次数和工具调用量。

这条链路的优点是即使 DeepSeek 不可用，核心场景也能通过本地规则展示；它本质上是“LLM 增强理解 + 确定性执行”，不是开放式 Agent 自主规划。

### 4.2 Agent Lab：DeepSeek 多轮 Tool Calling 链路

`/agent-lab` 是项目最能说明 Agent 能力的入口。浏览器先向 Python/FastAPI 的 `/api/cabin/session` 创建服务端演示会话，后续只提交会话 ID、用户请求及最近 8 条对话历史。服务端把系统提示词、14 个函数 Schema 和用户消息发送给 DeepSeek；模型自主选择函数，Python 服务端从会话读取状态、执行函数并写回会话，再把结果作为 `tool` 消息回传模型。

```text
浏览器
  │ 文本、有限会话历史、会话 ID
  ▼
Python FastAPI /api/cabin/session → /api/deepseek/agent
  │ 系统提示词 + 14 个函数 Schema
  ▼
DeepSeek 模型
  │ tool_calls
  ▼
服务端工具执行器
  │ Pydantic 校验参数、执行前置与安全规则、更新模拟状态、生成 Trace
  └──────── 工具结果回传 DeepSeek ────────┘
  ▼
最终回复 + 最新状态 + 调用轨迹 + 模型轮次/Token/延迟
```

单个请求最多执行 6 个模型轮次；单轮模型请求失败时服务端最多重试 3 次，前端 Agent Lab 和评测页在收到 502 时会额外重试整条请求 1 次。这些限制用于避免无限工具循环、外部网络瞬断和异常成本。

Agent Lab 还在主链路外侧补充了三类交互上下文：浏览器中文语音识别把结果放入输入框供用户复核，系统语音合成可播报 Agent 回复；用户点击授权后，WGS84 坐标、精度与外部算路同意随新会话写入服务端；普通目的地由 Nominatim 检索，道路路线由 OSRM 计算，界面使用 Leaflet/OpenStreetMap 展示距离、ETA、步骤、备选路线和预计到达电量。精确用户坐标与道路折线只保留在服务端会话和返回给浏览器的车辆状态，不进入大模型工具回执。

### 4.3 OpenAI Realtime：可选语音链路

`/realtime?agentConfig=cabinPilot` 使用 OpenAI Realtime Agents SDK。浏览器先向 `/api/session` 获取短期 client secret，再建立实时语音会话；用户可文字输入、语音输入、Push-to-Talk 和下载录音。

该入口同样挂载 `cabinPilotAgent` 和座舱工具，但它与 DeepSeek Agent Lab 是两条独立实现：

- Realtime 工具 Schema 使用英文枚举，如 `inside/outside`、`high_speed_confirmed`；
- DeepSeek 工具 Schema 使用中文枚举，如“内循环/外循环”、`confirmed`；
- 两条链路都使用本地模拟数据，但共享的安全语义并非同一个服务端工具模块。

当前环境没有配置可用的 `OPENAI_API_KEY`，因此 Realtime 页面会正常打开，但会提示未启用，`/api/session` 返回 503。不能把 Realtime 语音功能写为“已完成实测”。

## 5. Agent 的工具系统

核心产品是 1 个任务 Agent。Python 主实现位于 `backend/cabinguard/agent.py`，可选实时语音配置为 `cabinPilotAgent`。它能够调用以下 14 个工具：

| 工具 | 输入 | 返回/状态改变 | 业务目的与约束 |
| --- | --- | --- | --- |
| `get_vehicle_state` | 无 | 车速、挡位、电量、续航、位置来源、路线、目的地 | 车辆动作和补能前置读取 |
| `get_weather` | 当前位置 | 天气、降雨概率 | 打开天窗前置读取 |
| `get_climate_state` | 无 | 车内温度、设定温度、风量、循环模式 | 调节空调前置读取 |
| `set_climate` | 温度、风量、循环模式 | 更新空调模拟状态 | DeepSeek 路径限制温度 16–30℃、风量 1–5 档 |
| `search_charging_stations` | 是否顺路、最大绕行 | 演示候选站、坐标、距离、绕行、空闲桩、到站电量 | DeepSeek 路径强制先读取车辆状态 |
| `start_navigation` | 目的地 | 更新目的地、路线距离、ETA 与折线点 | 仅在用户明确要求导航且目的地属于本轮候选时调用 |
| `search_places` | 查询文本、候选数量 | Nominatim 候选 ID、名称、地址与来源 | 用户触发；坐标只保存到服务端会话 |
| `plan_navigation` | 候选 ID、路线偏好 | OSRM 道路距离、ETA、步骤、备选路线、折线、到达电量 | 显式导航意图、先读状态、先检索、候选绑定、定位同意 |
| `control_sunroof` | 开度、确认状态 | 更新天窗/遮阳帘，或返回阻止原因 | 降雨阻止；高速必须确认 |
| `control_trunk` | 开/关 | 更新后备箱状态或返回阻止结果 | 使用显式挡位；非 P 挡不允许开启 |
| `control_cabin_device` | 设备、区域、动作、值/颜色 | 更新车窗、座椅、氛围灯或除霜状态 | 先读车辆；严格动作配对；声明式拒绝/限幅 |
| `get_capabilities` | 无 | 实际工具、信号、约束和集成摘要 | 由运行时注册表生成，防止能力幻觉 |
| `manage_preferences` | remember/list/forget、键值 | 更新或读取当前会话偏好 | 写入/删除需要本轮用户明确授权 |
| `query_trip_history` | 无 | 最近成功导航形成的会话行程 | 只接受执行回执，最多 10 条 |

所有工具调用都会产生 `Trace`：工具名称、模型参数、工具输出和 `success/blocked` 状态。Agent Lab 把 Trace 展示给用户，评测页也会读取同一字段判断工具链是否符合预期。

## 6. 可信性与安全设计

项目的核心设计是把模型视为“不可信的规划层”，把服务端工具视为“最终动作边界”。模型可以建议调用什么工具和传什么参数，但不能直接修改车辆状态，也不能绕过工具层反馈成功。

### 已实现的软约束：系统提示词

- 调空调前先读取空调状态；
- 打开天窗前先读取车速与天气；
- 补能前先读取车辆电量、续航和路线；
- 高速天窗需要说明风险并得到明确确认；
- 模糊请求优先澄清；
- 未接入能力不能假称完成；
- 只有工具返回 `executed=true` 或 `navigation_started=true` 才能说任务完成。

### 已实现的硬约束：服务端工具执行器

- Python 主后端使用 Pydantic 严格校验所有工具参数，Next.js 兼容后端使用 Zod；非法类型、范围、枚举和多余字段不会被静默纠正为成功；
- `set_climate`、`search_charging_stations`、`control_sunroof` 和后备箱开启分别强制校验所需的状态读取前置；
- `control_sunroof` 在降雨概率不低于 50% 时拒绝打开；在车速不低于 80 km/h 且 `confirmed !== true` 时拒绝打开；
- `control_trunk` 在显式挡位不是 P 时拒绝打开；高速车窗超过 30% 时限幅，儿童锁开启时拒绝后排开窗；
- `start_navigation` 同时校验用户明确导航意图、搜索前置和本轮候选目的地；
- `plan_navigation` 只接受本会话地点候选 ID；浏览器真实起点还需外部算路同意，供应商失败时禁止生成替代假路线；
- 最终回复没有成功工具副作用作为依据时，服务端会替换无依据的完成表述；
- 模型最大 6 轮，服务端调用 DeepSeek 最多 3 次有限重试。

这种“提示词负责引导、工具层负责最终拦截”的分层是项目最值得面试时说明的技术设计。

## 7. 模拟数据与状态管理

当前车辆状态、天气、车控动作和固定充电站目录是模拟数据。初始状态包括：82 km/h、D 挡、38% 电量、176 km 续航、26.5℃车内温度、20% 降雨概率、京承高速模拟起点，以及两座固定的顺路充电站。普通地点和道路导航使用 Nominatim、OSRM 与 OpenStreetMap 真实公共数据。Agent Lab 会为每位使用者创建 30 分钟有效的服务端演示会话，并提供默认、降雨和行驶三种预置场景。用户可以主动授权浏览器定位；该坐标会记录为 `browser_geolocation` 来源，仍不属于可信车端状态。

状态的流向是：

- 主页：状态仅在 React 内存中更新；刷新页面即重置。
- Agent Lab：浏览器提交会话 ID；仅在用户主动授权定位时，创建新会话的请求额外携带坐标与精度。服务端读取并更新会话状态，前端以返回状态刷新 React State。
- Realtime：`cabinPilot.ts` 内另有模块级 `demoState`。

因此当前项目没有真实 CAN 总线、车端控制器、实时路况、车道级导航、充电站 API、用户账户、数据库或审计数据仓库。普通地点路线是真实道路规划，但公共服务没有生产 SLA；补能目录路线仍是演示沙箱。它能够证明工具编排、地图适配、安全交互和位置/导航数据契约，不能证明真实设备或量产地图平台能力。

## 9. 当前问题与生产化差距

### 必须如实说明的边界

1. **不是真实车控。** 当前车辆状态由服务端内存会话模拟；生产系统必须从可信车端网关或后端状态服务读取。
2. **只有演示级限流，没有身份认证。** 当前 DeepSeek Agent 路由按来源提供内存窗口限流，但没有用户身份、配额、持久化预算或分布式限流，公开部署仍有 API 成本和滥用风险。
3. **没有持久化。** 会话、状态和 Trace 不写入数据库，刷新后会丢失；评测报告仅下载到本地。
4. **Realtime 尚未启用验证。** 当前只有 DeepSeek 主链路可实际演示。
5. **模型行为评测尚未成为自动门禁。** 确定性规则已有 75 条 Pytest 与 39 条 Vitest；15 个模型任务仍需从页面或 Python CLI 主动运行并保存报告。
6. **跨链路参数不完全一致。** DeepSeek 空调风量为 1–5 档，Realtime 为 1–7 档；高速确认字段分别为 `confirmed` 与 `high_speed_confirmed`。后续接入真实后端前应统一契约。
7. **确认状态仍不是生产级授权。** 高速天窗确认已绑定会话、动作参数和 2 分钟有效期；生产环境仍应绑定任务 ID、车端签名、用户身份和审计记录。
8. **文案仍有语义歧义。** 天窗成功路径返回 `sunshade_percent: 100`，但模型曾描述为“遮阳帘保持全闭”；应在产品定义中统一百分比代表“开度”还是“闭合度”，并由前端模板化结果避免模型自行表述。
这些问题不影响把项目作为作品集 MVP 展示，但意味着它目前不能称为“生产级智能座舱系统”。

## 10. 面试和简历中可以准确表达的内容

### 可写的项目描述

> 设计并实现 CabinGuard 可信座舱任务 Agent，使用 Python、FastAPI 与 Pydantic 完成多轮编排、14 个领域工具、25 个 VSS 对齐信号、5 条声明式约束和会话记忆，构建“意图理解—状态读取—安全校验—工具执行—结果核验”闭环；接入 Nominatim/OSRM 真实地点与道路数据，并搭建 System Lab 与包含 15 个三类任务、五维评分和 Pass 一致性指标的 Reliability Lab。

### 可量化表述

- 完成 14 个领域工具和导航、补能、HVAC、车身、座椅、灯光、记忆等能力域；
- 设计 15 个覆盖明确任务、能力缺失和意图歧义的版本化任务，用同一会话验证多轮确认与补槽；
- 实现工具链、最终状态、策略、结果依据、不确定性五维确定性评分，以及 Pass^k / Pass@k 聚合；
- 旧版 10 类任务已完成定向复测；新版任务结果单独留档，不混用统计口径；
- Agent 请求最多 6 轮模型规划，单轮外部模型调用最多 3 次重试。

### 不应写的表述

- “14 Agent 多智能体智能座舱系统”；
- “已接入真实汽车/实时交通/真实充电网络”；
- “生产级车控平台”或“已量产”；
- “OpenAI Realtime 语音已稳定上线”；
- “10/10 自动化测试永久通过”。

## 11. 若要进入下一阶段，优先补齐的工作

1. DeepSeek 已使用统一领域工具执行层；下一步让主页和 Realtime 也通过同一服务端执行器，消除跨链路策略漂移。
2. 以车机模拟器或设备沙箱替换服务端演示会话；动作接口增加身份、权限、幂等键和审计日志。
3. 为 `/api/deepseek/agent`、`/api/session` 和可选 Realtime 接口加入鉴权、分布式限流、预算上限和超时控制。
4. 将 15 个任务扩展到 30–50 个同义表达、连续对话、网络失败和恶意提示用例，并形成足够样本量的置信区间。
5. 持久化任务、Trace、确认记录和评测报告，支持 Prompt、模型与工具版本的横向比较。
6. 配置 OpenAI Realtime 密钥后，单独完成语音输入、音频输出、工具调用和异常断连的实测；或从作品集导航中暂时隐藏未启用入口。
