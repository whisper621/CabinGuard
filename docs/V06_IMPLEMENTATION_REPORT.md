# CabinGuard v0.6 实施与评测报告

> 版本：0.6.0
> 结论：可信任务图纵向链路已经可运行；高级 DAG 调度、命令幂等、完整回放和真实身份认证仍属于后续工程，不在本报告中冒充完成。

## 1. 本次真正交付了什么

CabinGuard 已从“单 Agent 看见全部工具后自主调用”升级为以下可运行链路：

```text
用户请求
  → 服务端 TaskPlan 编译（目标 / 节点 / 依赖 / 波次 / 风险 / 权限 / 工具白名单）
  → 主 Agent 在受限工具范围内规划
  → Policy Kernel 校验 TaskPlan + 乘员 ABAC
  → 导航领域或确定性座舱服务执行
  → VSS 声明式约束做最终裁决
  → 状态版本递增
  → SQLite 写入计划、策略和工具证据
  → Mission / Twin Lab / Ops 页面展示
```

核心代码事实：

| 能力 | 实现文件 | 可观察证据 |
| --- | --- | --- |
| 可信任务图 | `backend/cabinguard/planning.py` | `POST /api/cabin/plan` 返回节点、依赖、执行波次和白名单 |
| 领域边界 | `backend/cabinguard/domains.py` | 能力清单返回 5 个领域 Manifest、工具范围、权限与 SLA |
| 多乘员权限 | `backend/cabinguard/policy_kernel.py` | 驾驶员、前排乘客、后排儿童、访客产生机器可读裁决 |
| 执行期闸门 | `backend/cabinguard/agent.py` | 每次工具调用先执行 TaskPlan + ABAC，不能只靠 Prompt |
| 因果证据账本 | `backend/cabinguard/event_store.py` | `GET /api/cabin/evidence/{session_id}` 返回 SQLite 事件 |
| 时序车辆状态 | `backend/cabinguard/signal_player.py` | 场景注入后状态版本递增，WebSocket 推送最新车辆状态 |
| 组合场景评测 | `backend/cabinguard/evaluation_v6.py` | 24 条场景验证领域、工具、越权隔离、权限和节点数 |
| 中文任务驾驶舱 | `src/app/mission/` | 计划预演、乘员角色、节点风险、工具回执与车辆状态 |
| VSS 数字孪生实验室 | `src/app/twin-lab/` | 注入城市/高速/驻车/降雨/低电量事件，显示状态时间线 |
| 编排与证据中心 | `src/app/ops/` | 按事件类型查看 planId、taskId、策略、状态版本和原始回执 |

## 2. “想实现”与“已经实现”的差距审计

这一节把方案文档视为产品意图，把服务端代码和测试视为实现事实。每个差距都说明影响对象和下一步修复，避免仅凭页面文案宣布完成。

| 意图主张 | 当前实现证据 | 差距与影响对象 | 下一步具体修复 |
| --- | --- | --- | --- |
| TaskPlan 直接驱动 DAG 并发执行 | `planning.py` 已生成拓扑波次；`agent.py` 仍由模型逐轮发起 Tool Calling | **部分实现。** 用户能看到正确计划，但运行顺序仍受模型选择影响；复杂任务可能多轮或漏调 | 增加 `dag_executor.py`，由调度器并发执行只读节点，写节点保持串行并继续过 Policy Kernel |
| 计划预览后由用户授权执行 | `/mission` 先请求计划，再立即请求 Agent | **部分实现。** 高风险工具仍有既有二次确认，但整张计划没有“确认执行”停顿；影响希望先审阅的驾驶员 | 将预览与执行拆成两个按钮；服务端签发短时 `planToken`，执行时校验计划版本 |
| 四类乘员 ABAC 是身份安全能力 | 会话创建时接收 `occupantRole`，服务端执行权限矩阵 | **原型级实现。** 角色值由浏览器提交，不是可信身份；影响真实车辆所有者与其他乘员 | 接入车机账号、座椅占用信号、设备证书；将角色改为服务端身份声明，客户端只能请求切换演示身份 |
| 每个写动作具备幂等键和乐观并发 | 会话已有 `stateVersion`，Trace 记录执行前后版本 | **尚未实现命令校验。** 重试可能重复执行写操作；受影响者是网络抖动下的乘员和车辆状态 | 工具请求增加 `commandId`、`expectedStateVersion`；服务端保存结果并拒绝陈旧版本或重复命令 |
| VSS 10 Hz 时序数字孪生、暂停、倍速、重放 | `signal_player.py` 提供离散事件；WebSocket 250 ms 轮询状态版本 | **纵向切片。** 可以展示状态演进，不能声称连续物理仿真或完整回放；影响具身/仿真评审者 | 增加带时间戳的 ScenarioScript、虚拟时钟、sequence、暂停/单步/倍速和事件重放测试 |
| 任意任务可追踪到最终回复 | 账本已有 `plan.created`、`policy.decision`、`tool.receipt`、`signal.injected` | **部分实现。** 尚无 `agent.response`、父子 Span 时长和成本事件；影响故障定位与成本分析 | 写入回复、模型轮次、Token、延迟和外部 Provider Span；生成稳定 `traceId` 并建立父子关系 |
| 导航领域 Agent 使用独立推理上下文 | `domains.py` 已形成独立 Manifest、白名单、权限和执行器边界 | **逻辑边界已实现，模型隔离未实现。** 当前仍复用主 Agent 的 DeepSeek 上下文；影响超长导航任务的上下文控制 | 在确有收益的导航歧义任务上增加独立 prompt/context budget，并用实验比较成功率、成本和延迟 |
| 全站中文优先 | Mission、Twin、Ops 和关键导航已中文化；技术代码名只在详情中出现 | **核心页实现。** 经典页面仍保留少量 Agent Lab、Token 等行业词；影响非技术面试官的第一眼理解 | 将旧 System Lab、Case Study 的剩余英文建立统一字典，保留英文只作为括注 |

## 3. 组合评测设计

### 3.1 评测对象

`evaluation/composite_cases.json` 包含 24 个版本化场景，覆盖：

- 单域：空调、导航、补能、天窗、后备箱、车窗、座椅、氛围灯、天气、能力、车辆状态、记忆；
- 跨域：空调 + 导航、车窗 + 导航、天气 + 天窗、天气 + 除雾；
- 权限：驾驶员、前排乘客、后排儿童、访客；
- 安全：不相关工具不得进入任务白名单，未授权角色的写操作必须拒绝。

评分指标：领域召回、预期工具召回、禁止工具精度、权限结果匹配、任务节点数匹配。该评测不调用大模型，因此可以进入持续集成；15 条既有模型行为评测继续负责工具顺序、最终状态、依据和澄清能力。

### 3.2 代表性测试场景

| 测试目标 | 起始条件 | 用户角色 | 操作步骤 | 可观察预期结果 | 边界情况 |
| --- | --- | --- | --- | --- | --- |
| 验证跨域 DAG | 默认车辆、无目的地 | 驾驶员 | 输入“空调调到 22 度并导航去故宫” → 预演 | 出现系统、舒适、导航三领域；`set_climate` 依赖空调读取，路线规划依赖地点检索 | `control_trunk` 不得出现在白名单 |
| 验证儿童写权限 | 默认车辆、儿童锁状态可变 | 后排儿童 | 输入“把后排车窗打开一半” → 执行 | TaskPlan 可表达请求；Policy Kernel 返回 `guardian_authorization_required`；状态版本不因拒绝而变化 | 即使模型给出合法参数也必须拒绝 |
| 验证访客导航权限 | 默认车辆、有外部地图服务 | 访客 | 输入“导航去上海虹桥站” → 执行 | 地点读取可允许；`plan_navigation` 写动作返回 `occupant_role_forbidden` | 外部候选存在也不能绕过角色限制 |
| 验证雨天天窗 | 先在 Twin Lab 注入降雨 | 驾驶员 | 请求打开天窗 | TaskPlan 包含车辆、天气和天窗节点；VSS 约束拒绝开启；账本保留策略与工具回执 | 关闭天窗应允许，不把“雨天”误解为禁止所有天窗动作 |
| 验证信号状态版本 | 新会话状态 v1 | 驾驶员 / 实验员 | 注入高速事件 → 注入低电量事件 | WebSocket 依次收到新版本；速度、电量和续航展示变化；Ops 出现两条 `signal.injected` | 断连不应修改服务端状态；过期会话返回明确事件 |
| 验证证据闭环 | 已成功执行一次空调任务 | 驾驶员 / 面试官 | 打开 Ops → 按事件筛选 | 可看到同一 planId 下的计划、策略和回执，Trace 含 taskId 与执行前后状态版本 | 空会话提供引导，不伪造历史证据 |

## 4. 参考项目如何影响了实现

- `p1-cabin-agent` 的多意图波次、状态黑板和槽位延续启发了 TaskPlan 的依赖与 `executionWaves`；CabinGuard 用 Pydantic + FastAPI 独立实现，并将安全授权放在任务执行前。
- `cockpit-agent-sim` 的“工具是机制、Agent 是策略”、声明式车辆信号约束、控制台/车机界面分离和机器可读拒绝协议影响了 Domain Manifest、Policy Kernel、Twin Lab 与 Ops 的职责划分。
- CabinGuard 没有照搬两者的全部功能。作品集的差异点是“可信出行任务图 + 多乘员权限 + 状态版本 + 因果证据”，而不是工具数量竞赛。

## 5. 面试时可以准确怎么说

> 我把 CabinGuard 从一个能调用 14 个工具的座舱 Agent，升级成了可信的协同任务系统。用户一句跨域需求先被编译成带依赖、风险、权限和工具白名单的 TaskPlan；每次执行再经过乘员/设备/座位 ABAC 与 VSS 约束，结果连同状态版本写入 SQLite 证据账本。前端分别用任务驾驶舱、数字孪生实验室和证据中心展示“计划—环境变化—执行—复盘”。目前 24 条组合契约和 130 条确定性测试通过；车辆控制仍是沙箱，真实地图使用公共服务，独立导航模型上下文、幂等命令与完整时序回放是下一阶段。

这段表述同时说明价值、架构、证据和边界，适合 AI 产品经理、智能座舱产品经理与具身智能产品经理面试。
